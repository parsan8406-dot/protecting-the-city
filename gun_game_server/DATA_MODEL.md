# دسته‌بندی دیتای بازی — دیتابیس در برابر کلاینت

این سند مرجع تصمیم‌گیری است: هر داده‌ای که در منوهای بازی می‌بینیم، در یکی از دو
دسته‌ی زیر قرار می‌گیرد.

معیار تصمیم‌گیری ساده است:

| سوال | اگر جواب «بله» بود |
|---|---|
| اگر بازیکن اپ را پاک کند، باید از بین برود؟ | کلاینت |
| بازیکن دیگری هم باید این را ببیند؟ | دیتابیس |
| اگر بازیکن دستکاری‌اش کند، تقلب محسوب می‌شود؟ | دیتابیس |
| به «دستگاه» وابسته است نه به «اکانت»؟ | کلاینت |

---

## بخش اول — دیتای دیتابیس (MongoDB / `gun_game_db`)

### ۱. کالکشن `players`
منبع واحد حقیقت برای هویت، دارایی و آمار بازیکن.

| گروه | فیلدها | از کدام منو می‌آید |
|---|---|---|
| هویت | `player_id`, `username`, `avatar_id`, `frame_id`, `country_code` | نوار بالا، پروفایل، دوستان (ID : ۴۵۱۳۵) |
| اقتصاد | `coins`, `gems` | نوار بالا (سکه / جم) |
| پیشرفت | `level`, `experience` | نوار بالا و پروفایل (سطح ۲۱ — ۳۰۰/۵۲۵۲۶) |
| مالکیت | `owned_weapons`, `owned_characters` | فروشگاه |
| تجهیزات | `equipped_weapon`, `equipped_character` | فروشگاه / بازی |
| آمار (`stats`) | `total_matches`, `wins`, `losses`, `kills`, `deaths`, `assists`, `playtime_seconds`, `missions_done`, `grenade_kills`, `heals_given`, `last_used_weapon` | پروفایل → کارت آمار و «آخرین سلاح مورد استفاده» |
| رتبه (`rank`) | `season_id`, `tier_id`, `tier_name`, `division`, `points`, `points_max`, `best_tier_id` | پروفایل → کارت «فصل / لجند / رتبه ۵» |
| دستاورد | `achievements[]` (`achievement_id`, `unlocked_at`) | پروفایل → تازه‌ترین دستاوردها |
| شهر | `clan_id`, `clan_role` | پروفایل → شهر عضو شده |
| اجتماعی | `friends[]`, `blocked[]` | منوی دوستان |
| اکانت (`auth`) | `provider`, `is_guest`, `email`, `email_verified`, `google_id`, `google_name`, `linked_at`, `sessions[]` (`token_hash`, `device`, `created_at`), `last_login_at` | تنظیمات → اتصال با گوگل / ورود با گوگل |
| فرم اخیر | `recent_matches[]` (۱۰ تای آخر: `mode_id`, `won`, `draw`, `kills`, `deaths`, `weapon`, `at`) | پروفایل → نقطه‌های «فرم اخیر» |
| پیام همگانی | `read_broadcasts[]`, `hidden_broadcasts[]` | پیام‌ها — خوانده/حذف شدنِ پیام `"*"` برای هر بازیکن جدا |
| وضعیت | `is_online`, `last_seen_at`, `is_banned` | دوستان → نقطه سبز آنلاین |
| نظارت (پنل مدیریت) | `ban_reason`, `banned_at`, `banned_until` (خالی = دائمی), `chat_muted_until` | — هیچ‌کدام در JSON کلاینت نمی‌آیند |
| متادیتا | `created_at`, `updated_at` | — |

**فیلدهای محاسبه‌شده (ذخیره نمی‌شوند، در پاسخ API ساخته می‌شوند):**
`win_rate` (درصد برد)، `kd_ratio`، `playtime_hours`، `display_xp`، `max_xp`، `unread_messages`.

> نکته امنیتی: `password_hash`، `google_id`، ایمیل و `sessions` هرگز در خروجی
> JSON نمی‌آیند (تگ `json:"-"`). از توکن دستگاه فقط هش SHA-256 ذخیره می‌شود.

### ۱.۱ احراز هویت و اتصال به گوگل (`handlers_auth.go`)

- **توکن دستگاه**: حساب تازه موقع اولین `GET /get_player` یک توکن ۳۲ بایتی
  می‌گیرد (`session_token` فقط همان یک بار در پاسخ). کلاینت آن را در
  `user://account.cfg` (بخش `sessions`) نگه می‌دارد و روی هر درخواست
  `Authorization: Bearer <token>` می‌فرستد، و در `join` وب‌سوکت فیلد `token`.
  حداکثر ۵ دستگاه؛ قدیمی‌ترین کنار می‌رود. حساب‌های قدیمیِ بی‌دستگاه، اولین
  دستگاهی را که بیاید مالک می‌شناسند (`claimFirstSession`).
- **حساب محافظت‌شده** = `auth.google_id` دارد. `authGuard` (روی همه‌ی مسیرها)
  هر درخواستی را که `username` آن — در query یا بدنه‌ی JSON، هر دو بررسی
  می‌شوند — مال یک حساب محافظت‌شده باشد و توکن معتبر نداشته باشد با
  `401 {"code":"auth_required"}` رد می‌کند. join وب‌سوکت هم همین‌طور.
  حساب‌های مهمان رفتار قبلی را دارند.
- **اتصال** فقط از دستگاهِ تأییدشده‌ی همان حساب ممکن است (جلوی دزدیدن حساب
  با چسباندن گوگلِ خود به اسم دیگری را می‌گیرد). یک حساب گوگل = یک حساب بازی
  (ایندکس یکتای `uniq_google_id`).
- **بازیابی**: روی گوشی تازه «ورود با گوگل» حسابِ وصل‌شده را پیدا می‌کند و
  یک توکن دستگاه تازه می‌دهد.
- **جریان مرورگری** (بدون پلاگین بومی): `start` → کلاینت آدرس گوگل را با
  `OS.shell_open` باز می‌کند → گوگل به `callback` برمی‌گردد → سرور code را با
  PKCE (S256) و `client_secret` عوض می‌کند و ادعاهای `id_token` (iss/aud/exp)
  را بررسی می‌کند → کلاینت با `poll` نتیجه را یک‌بار برمی‌دارد. خودِ
  `poll_secret` ذخیره نمی‌شود (فقط هش)، و توکن ورود همان لحظه‌ی poll ساخته
  می‌شود. جریان‌های نیمه‌تمام در کالکشن `auth_google_pending` با TTL ده دقیقه.
- **پلاگین بومی** (اختیاری): `id_token` را به `POST /auth/google/token` بدهد؛
  سرور آن را با `tokeninfo` خودِ گوگل تأیید می‌کند.

متغیرهای محیطی سرور:

| متغیر | کار |
|---|---|
| `GOOGLE_CLIENT_ID` | کلاینت OAuth نوع Web application |
| `GOOGLE_CLIENT_SECRET` | رمز همان کلاینت (فقط روی سرور) |
| `PUBLIC_BASE_URL` | آدرس عمومی سرور؛ redirect URI در کنسول گوگل: `<PUBLIC_BASE_URL>/auth/google/callback` |
| `GAME_SERVER_KEY` | کلید سرویس‌های داخلی برای `POST /match/result` (هدر `X-Server-Key`)؛ بدون آن این مسیر بسته است |

### ۱.۲ آمار پروفایل و دستاوردها (`achievements.go`)

آمار پروفایل از خودِ راند در هاب ثبت می‌شود (`persistProfileStats` از
`persistMatchMissions`): کشته، مرگ، نارنجک، درمان، زمان بازی، `last_used_weapon`
و `recent_matches`. برد/باخت و کاپ همچنان با `ApplyMatchResult`؛ مساوی فقط
به `total_matches` اضافه می‌شود. بعد از هر راند (و هر بار که بازیکن پروفایل
خودش را باز می‌کند) دستاوردهای واجد شرایط با آپدیت شرطی اتمیک باز می‌شوند و
جایزه‌شان به‌صورت پیام می‌آید. کاتالوگ ۱۸ دستاورد دارد (`achievementCatalog`) و
پله‌های اولش همان مسابقه‌ی اول باز می‌شوند.

### ۲. کالکشن `messages` — منوی «پیام ها»
`message_id`, `recipient_id` (یا `"*"` برای پیام همگانی), `sender_id`, `sender_name`,
`type` (`system` | `friend_request` | `gift` | `reward` | `admin`), `title`, `body`,
`reward` (سکه/جم/آیتم), `reward_claimed`, `ref_id`, `is_read`, `read_at`,
`created_at`, `expires_at`.

- `is_read` همان تیک دوتایی گوشه‌ی پیام است.
- `expires_at` ایندکس TTL دارد؛ خود MongoDB پیام‌های منقضی را پاک می‌کند.
- آیتم «درخواست دوستی» در لیست پیام‌ها یک `MessageModel` با `type=friend_request`
  است که `ref_id` آن به `friend_requests` وصل می‌شود.

### ۲.۱ کالکشن `support_messages` — پیام کاربر به سازنده
تنظیمات → دکمه‌ی «ارسال پیام». کاربر باکس را باز می‌کند، با کیبورد گوشی متن را
می‌نویسد و «ثبت» را می‌زند.

`ticket_id`, `username`, `player_id`, `body`, `platform`, `app_version`,
`status` (`new` | `read` | `answered`), `created_at`.

- بر خلاف `messages` که صندوق **ورودی بازیکن** است، این کالکشن صندوق **ورودی
  سازنده** است؛ جهت پیام برعکس است.
- سرور `username` را از روی رکورد بازیکن بازنویسی می‌کند، پس کلاینت نمی‌تواند
  به‌جای کس دیگری پیام بفرستد.
- محدودیت ضد اسپم: حداکثر ۵ پیام در هر ۱۰ دقیقه برای هر بازیکن.
- دیدن و جواب دادن: پنل مدیریت → «پشتیبانی» (بخش ۱۰). پاسخ به‌صورت پیامِ
  `type=admin` در صندوقِ خودِ بازیکن می‌نشیند و در `replies[]` تیکت ثبت می‌شود.
  وضعیت `closed` هم اضافه شده. `GET /support/messages` حالا فقط با `X-Server-Key`
  باز است (قبلاً برای همه باز بود و پیام همه‌ی بازیکن‌ها را نشان می‌داد).

### ۳. کالکشن `friend_requests` — دکمه‌های «پذیرفتن» و ضربدر
`request_id`, `from_id`, `from_username`, `to_id`, `to_username`,
`status` (`pending`/`accepted`/`rejected`/`cancelled`), `created_at`, `responded_at`.

ایندکس یکتای جزئی روی `(from_id, to_id)` وقتی `status = pending` مانع اسپم درخواست می‌شود.

### ۴. کالکشن `clans` — «شهر»
`clan_id`, `name`, `tag`, `description`, `icon_path`, `level`, `experience`,
`max_members`, `members[]` (`player_id`, `username`, `role`, `joined_at`),
`owner_id`, `is_public`, `min_level`, `created_at`.

نمایش «سطح ۱۰ / اعضا ۲۵/۵۰» از `level` و `len(members)/max_members` ساخته می‌شود.

**نقش‌ها** (`members[].role` و `players.clan_role` که با هم همگام نگه داشته می‌شوند):
`leader` > `officer` > `member`. اختیارات با مقایسه‌ی همین ترتیب سنجیده می‌شود —
هر کس فقط روی نقش‌های **پایین‌تر از خودش** می‌تواند عمل کند:

| کار | حداقل نقش لازم |
|---|---|
| پذیرفتن/رد درخواست عضویت | `officer` |
| اخراج عضو | `officer` (فقط روی نقش پایین‌تر) |
| ارتقا/تنزل نقش | `leader` |

**عمومی در برابر خصوصی**: شهر با `is_public=true` بازیکن واجد شرایط را بدون واسطه
عضو می‌کند؛ شهر خصوصی به‌جایش یک رکورد در `clan_requests` می‌سازد.

**ترک شهر**: اگر رهبر برود و کسی مانده باشد، رهبری خودکار به قدیمی‌ترین معاون
(و اگر معاونی نبود، قدیمی‌ترین عضو) می‌رسد. اگر آخرین نفر برود، خود شهر و
درخواست‌های بازش حذف می‌شوند.

> نکته‌ی همزمانی: عضو شدن با شرط `$expr: {$lt: [{$size: "$members"}, "$max_members"]}`
> روی همان آپدیت انجام می‌شود، و کم شدن سکه‌ی ساخت شهر با شرط `coins >= هزینه`.
> این‌طور دو درخواست هم‌زمان نمی‌توانند از ظرفیت آخر یا یک موجودی دوبار رد شوند.

### ۴.۱ کالکشن `clan_requests` — درخواست عضویت در شهر خصوصی
`request_id`, `clan_id`, `clan_name`, `from_id`, `from_username`, `from_level`,
`from_avatar_id`, `status` (`pending`/`accepted`/`rejected`), `created_at`, `responded_at`.

ایندکس یکتای جزئی روی `(clan_id, from_id)` وقتی `status = pending` مانع اسپم
درخواست می‌شود — دقیقاً همان الگوی `friend_requests`.

### ۵. کالکشن `achievements` — کاتالوگ (دیتای استاتیک بازی)
`achievement_id`, `name`, `description`, `icon_path`, `metric`, `target`,
`reward_coins`, `reward_gems`, `sort_order`.

تعریف دستاورد در این کالکشن است؛ **باز شدنش** در `players.achievements` ذخیره می‌شود.

### ۶. کالکشن `seasons` — فصل رقابتی
`season_id`, `name`, `starts_at`, `ends_at`, `is_active`, `tiers[]`
(`tier_id`, `name`, `divisions`, `points_per_division`).

### ۶.۱ کالکشن `season_cups` — کاتالوگ کاپ‌های فصل

`cup_id`, `season_id`, `name`, `xp_required`, `reward_coins`, `reward_gems`,
`icon`, `sort_order`. ایندکس یکتا روی (`season_id`, `cup_id`).

این کالکشن **منبع حقیقتِ صفحه‌ی رنک → «کاپ ها»** است. کلاینت هیچ لیستی از
کاپ‌ها ندارد؛ فقط چیزی را نشان می‌دهد که `GET /season/cups` از این کالکشن
خوانده. باز بودن هر کاپ را هم سرور با مقایسه‌ی `xp_required` و تجربه‌ی فصلِ
داخل سند بازیکن حساب می‌کند.

**گرفتنِ کاپ** در `players.season_cups` می‌نشیند:

```
season_cups: { season_id: "season_1", claimed: ["cup_01", ...] }
```

`POST /season/cups/claim` فقط `cup_id` می‌گیرد؛ مقدار جایزه و تجربه‌ی لازم را
از دیتابیس می‌خواند و با یک آپدیت شرطیِ اتمیک
(`season_cups.claimed: {$ne: cup_id}`) واریز می‌کند — پس نه می‌شود کاپ قفل را
گرفت و نه یک کاپ را دو بار.

`seed` اولیه در `season_cups.go` است و با `$setOnInsert` می‌نویسد، یعنی اگر
عددی را مستقیم در دیتابیس عوض کنی، ری‌استارت سرور آن را برنمی‌گرداند.

### ۶.۲ کالکشن `game_modes` — حالت‌های بازی و قانونشان

`mode_id`, `name`, `subtitle`, `description`, `team_size`, `accent`,
`win_trophies`, `win_coins`, `win_xp`, `lose_trophies`, `lose_coins`, `lose_xp`,
`min_trophies`, `sort_order`, `is_active`.

`seedGameModes` عمداً داکیومنتِ موجود را دست نمی‌زند تا اعدادِ اقتصاد که دستی
تنظیم شده‌اند با هر ری‌استارت پاک نشوند. ولی ساختارِ خودِ حالت اقتصاد نیست:
`MigrateGameModes` مقدارهایی مثل `team_size` را روی داکیومنت‌های قدیمی هم
اصلاح می‌کند.

**قانونِ راند در دیتابیس نیست، در کد است** (`match_round.go` → `rulesForMode`).
دلیلش ساده است: قانون چیزی است که سرور اجرا می‌کند و تست دارد، نه چیزی که
ادمین وسطِ بازی عوضش کند.

| حالت | نفرات | مدت | مرگ | برنده | محافظِ تولد |
|---|---|---|---|---|---|
| عملیات ضربت / حذف شیطان / امتیاز شهر | ۴ / ۳ / ۳ در هر تیم | ۳ دقیقه | حذف، بی‌بازگشت | آخرین تیمِ زنده | ۳ ثانیه |
| **عملیات انتقام** | **۱ در ۱ (دو بازیکن)** | **۲ دقیقه** | **۳ ثانیه بعد برمی‌گردی** | **هر که بیشتر زده** | **۵ ثانیه** |

محافظِ تولد واقعی است، نه گرافیک: تا `players.invulnerable_until` (فقط در رم)
نگذشته، `validateHit` و `applyBombDamageInternal` هیچ ضربه‌ای را قبول نمی‌کنند.
باقی‌مانده‌اش در هر `update_players` به‌صورت `shield_left` می‌رود تا کلاینت
گنبد را دقیقاً به‌اندازه‌ی همان مدت بکشد.

### ۶.۳ زمین‌های بازی (فایل، نه کالکشن)

`arena_map.json` و `arena_revenge.json` — کنارِ سرور با `go:embed` داخل باینری
می‌روند و نسخه‌ی دومشان در `resources/` برای گودوت است. هر دو با
`python tools/build_arena.py` از یک منبع ساخته می‌شوند، پس کلاینت و سرور
هیچ‌وقت دو نقشه‌ی متفاوت ندارند.

نگاشتِ حالت به زمین در `arena.go` → `mapForMode` است؛ حالتی که زمینِ اختصاصی
ندارد روی زمینِ پیش‌فرض می‌افتد. زمینِ هر بازیکن لحظه‌ی `join` روی خودش
می‌نشیند (`Player.Arena`)، پس اعتبارسنجیِ حرکت و خطِ دید همیشه با همان نقشه‌ای
انجام می‌شود که خودش می‌بیند.

زمینِ «عملیات انتقام» بازتر است (۳×۲ اتاق، درهای پهن، ستون‌های پناه‌گیری) چون
آن‌جا مرگ موقتی است و بازی باید جریان داشته باشد، نه اینکه گوشه‌گیری جواب بدهد.

### ۷. کالکشن `matches` — تاریخچه مسابقات
`match_id`, `mode`, `map_name`, `started_at`, `ended_at`, `duration_seconds`,
`participants[]` (`player_id`, `kills`, `deaths`, `assists`, `grenade_kills`,
`heals_given`, `won`, `xp_gained`, `coins_gained`, `rank_delta`, `weapon_used`).

این کالکشن **منبع تولید آمار پروفایل** است. سرور بعد از هر بازی یک رکورد اینجا
می‌سازد و بعد `players.stats` را با `$inc` بالا می‌برد. مزیتش این است که اگر
فرمول آمار عوض شد، می‌شود دوباره از روی همین داده‌ها بازسازی کرد.

### ۸. کالکشن `shop_items` — تراز و قیمت

مدلِ پایه همان قبلی است، به‌علاوه‌ی دو چیز که سرور هر بار بالا آمدن از نو
می‌نویسد (`SeedCharacterStats` و `SeedCatalogPrices` در `db.go`):

**الف) `stats` — ویژگی‌های گیم‌پلیِ کاراکتر** (فقط برای نمایش در فروشگاه)

| کلید | معنی |
|---|---|
| `pip_vitality`, `pip_speed`, `pip_firepower`, `pip_bomb_reach`, `pip_bomb_power` | امتیازهای خام ۱ تا ۵ (برای میله‌های فروشگاه) |
| `pip_total` | جمعشان — همیشه ۱۵ |
| `health`, `speed`, `damage` | عددهای واقعی در سطح ۱ |
| `bomb_range`, `bomb_radius`, `bomb_damage` | برد پرتاب، شعاع و خسارتِ انفجار در سطح ۱ |
| `max_level` | سقف ارتقا (rare ۵، epic ۸، legend ۱۰) |
| `max_health`, `max_damage`, `max_bomb_range`, `max_bomb_radius`, `max_bomb_damage` | همان عددها بعد از ارتقای کامل |

> ⚠️ **این‌ها منبع حقیقت نیستند.** عددهای گیم‌پلی از `balance.go` خوانده
> می‌شوند، نه از دیتابیس. این کپی فقط برای رابط کاربری است تا بازیکن قبل از
> خرید ببیند چه می‌خرد. دست‌کاری دیتابیس روی تعادلِ بازی اثر ندارد.

**قانون تعادل** (`balance.go`): درون هر رده همه دقیقاً ۱۵ امتیاز دارند — پس
دو اسکینِ هم‌رده هیچ‌کدام از دیگری قوی‌تر نیست، فقط جای امتیازهایشان فرق
می‌کند. بین رده‌ها یک برتریِ کم هست (epic ۳٪، legend ۶٪) که فقط روی
سلامت/خسارت اعمال می‌شود، نه روی سرعت و برد.

**ب) قیمت** فقط از رده و نوع آیتم می‌آید (`pricing.go`):

| | rare | epic | legend |
|---|---|---|---|
| کاراکتر | ۶۰۰۰ سکه | ۲۰۰ جم | ۴۵۰ جم |
| سلاح | ۴۰۰۰ سکه | ۱۵۰ جم | ۳۵۰ جم |

آیتم‌های شروع (`skin_default`، `ak47`، `pistol_default`) رایگان‌اند چون
بازیکن از اول دارِدشان. تخفیف‌های ویترین دست‌نخورده می‌مانند.

### ۸.۱ سطحِ ارتقای آیتم‌ها — `players.item_levels`

`map[item_id]level`. آیتمی که در این نگاشت نباشد سطح ۱ است. سقفِ هر آیتم از
رده‌اش می‌آید و سرور موقع محاسبه‌ی تراز خودش clamp می‌کند، پس مقدارِ نامعتبر
خطرناک نیست. سیستمِ خرید ارتقا هنوز اضافه نشده — این فقط جای ذخیره‌اش است.

### ۱۰. پنل مدیریت (`admin_*.go`، صفحه در `admin_panel/`)

صفحه‌ی وب داخل همین باینری (`go:embed`) روی `ADMIN_PATH` (پیش‌فرض `/admin/`)؛ API زیر `<ADMIN_PATH>/api/`.
بدون `ADMIN_ACCOUNTS` در `.env` کاملاً خاموش است (404).

```
ADMIN_ACCOUNTS=parsa:admin:<رمز>,ali:support:<رمز>
```

رمز حداقل ۱۰ حرف، حساب‌ها با ویرگول جدا. نقش `admin` همه‌کار؛ نقش `support`
پشتیبانی، پیام بدون جایزه به بازیکن مشخص، نظارت چت عمومی، بستن چت و مسدودیتِ
حداکثر ۷ روزه — به اقتصاد، جایزه، پیام همگانی، کد هدیه، چت خصوصی، شهر،
فروشگاه و حالت‌های بازی دست نمی‌زند.

امنیت (`admin_security.go`):

| لایه | تنظیم |
|---|---|
| رمز فقط هش PBKDF2-SHA256 (۶۰۰هزار دور) | `ADMIN_ACCOUNTS=user:role:pbkdf2-sha256$...` + `ADMIN_REQUIRE_HASH=1` — هش با `gun_game_server admin-hash` |
| کد دومرحله‌ای TOTP (Google Authenticator)، هر کد یک‌بار | `ADMIN_TOTP_<USER>=<base32>` + `ADMIN_REQUIRE_TOTP=1` — کلید با `gun_game_server admin-totp <user>` |
| آدرس مخفی (مسیر `/admin` 404 می‌دهد) | `ADMIN_PATH=/gg-...` |
| قفل سراسری: ۲۰ ورود ناموفق در ۱۵ دقیقه ← ورود ۱۵ دقیقه بسته | — |
| نشست: ۱ ساعت بی‌کاری / ۱۲ ساعت کل، در حافظه | — |
| کوکی `HttpOnly` + `Secure` (وقتی `PUBLIC_BASE_URL` https است) + `SameSite=Strict` روی مسیر پنل، `X-Admin-CSRF` روی هر POST، CSP سخت‌گیر | — |
| سقف هر تغییرِ دارایی (۱۰م سکه، ۱۰۰هزار قلب) | — |

**قفل اضطراری («هک شدم»)**: از داخل پنل (هر نقشی) یا از صفحه‌ی ورود با کلید
اضطراری (`ADMIN_PANIC_KEY_SHA256`، کلید با `gun_game_server admin-panickey`).
همه‌ی نشست‌ها باطل و ورود بسته می‌شود (`423`)، و اختیاری همه‌ی کدهای هدیه غیرفعال
و پیام‌های جایزه‌دارِ دریافت‌نشده‌ی ۲۴ ساعت اخیرِ پنل پاک می‌شوند. وضعیت در
کالکشن `admin_state` می‌ماند و ری‌استارت بازش نمی‌کند؛ فقط از روی سرور:
`cd /opt/gungame && ./gun_game_server admin-unlock && systemctl restart gungame`.
اگر وضعیت از دیتابیس خوانده نشود پنل قفل می‌ماند. بازی برای بازیکن‌ها قطع نمی‌شود.

| کالکشن | کار |
|---|---|
| `admin_audit` | هر کارِ ادمین (`at`, `admin`, `action`, `target`, `details`, `ip`) — ورود ناموفق هم |
| `admin_notes` | یادداشت داخلی روی بازیکن |
| `admin_campaigns` | پیام‌های ارسالی از پنل؛ پیام‌ها با `ref_id = campaign_id` به آن وصل‌اند |
| `admin_state` | سند `lockdown` — قفل اضطراری |

**مسدودیت**: `authGuard` و `join` وب‌سوکت حسابِ مسدود را با
`403 {"code":"banned"}` رد می‌کنند و بازیکن همان لحظه از هاب بیرون انداخته می‌شود.
کلاینت متن خطا را روی صفحه‌ی بارگذاری نشان می‌دهد و خارج می‌شود. مسدودیتِ موقت
بعد از `banned_until` خودش تمام می‌شود و پرچمش هم پاک می‌شود.

**پیام از پنل**: همگانیِ بدون جایزه = یک سند `"*"`. جایزه‌دار یا «فعال‌های اخیر»
= یک سند برای هر بازیکن (قفل یک‌بار دریافت روی خود پیام است). «پس گرفتن» پیام‌های
باقی‌مانده را حذف می‌کند؛ جایزه‌ی دریافت‌شده برنمی‌گردد.

**تغییر دارایی**: با `$max: 0` اتمیک است (هیچ‌وقت منفی نمی‌شود) و سطح از روی
تجربه دوباره حساب می‌شود؛ دلیلِ تغییر اجباری است و در تاریخچه می‌ماند.

**عمداً نیست**: تغییر نام بازیکن (کلاینت اسم و توکن را محلی نگه می‌دارد و حساب
یتیم می‌شد)، حذف حساب، و باطل کردن دستگاه‌ها (حساب بی‌دستگاه را اولین کسی که
اسمش را بداند تصاحب می‌کند — `claimFirstSession`).

## بخش دوم — دیتای کلاینت (فایل `user://settings.cfg`، اتولود `LocalSettings`)

این‌ها **هیچ‌وقت** به دیتابیس نمی‌روند، چون به دستگاه وابسته‌اند نه به اکانت.

### الف) دائمی روی دستگاه (`scripts/LocalSettings.gd`)

| گروه | مقادیر | منو |
|---|---|---|
| صدا | `master_volume`, `sfx_volume`, `ambient_volume`, `music_volume` | تنظیمات → صدا |
| تصویر | `brightness`, `quality` | تنظیمات → تصویر |
| رابط کاربری | `language`, `vibration_enabled`, `show_fps`, `joystick_side` | تنظیمات |

دکمه «بازنشانی تنظیمات» فقط `LocalSettings.reset_to_defaults()` را صدا می‌زند —
هیچ درخواستی به سرور نمی‌رود.

### ب) موقت، فقط تا بسته شدن بازی (حافظه)

- تب فعال منو، دوست انتخاب‌شده در لیست، موقعیت اسکرول
- کش تکسچر آواتارها و آیکن‌ها
- انیمیشن‌ها، تایمر شمارش معکوس، افکت‌ها
- ورودی جوی‌استیک، لمس‌ها
- دیتای گرفته‌شده از سرور که در `Global.gd` کش می‌شود (نسخه‌ی خواندنی، نه منبع حقیقت)

### ج) فقط در رم سرور (نه دیتابیس، نه کلاینت) — `hub.go`

موقعیت `x`/`y`، زاویه `rot`، جان فعلی، کول‌داون درمان و بمب، ایمنی ابتدای بازی،
و آمار همان راند. اینها با قطع اتصال از بین می‌روند و فقط نتیجه‌ی نهایی راند
از طریق `/match/result` در دیتابیس ثبت می‌شود.

> نکته ضدتقلب: جان، برد و کیل هرگز نباید از کلاینت قابل ست شدن باشند. کلاینت
> فقط «قصد» می‌فرستد (`hit`, `heal`, `bomb`) و سرور تصمیم می‌گیرد.

### د) موارد مرزی

| داده | تصمیم فعلی | دلیل |
|---|---|---|
| صدا و روشنایی | کلاینت | وابسته به دستگاه |
| زبان | کلاینت | اگر بعداً پیام‌های سرور ترجمه شدند، به دیتابیس منتقل شود |
| نوتیفیکیشن‌ها | فعلاً کلاینت | برای push notification باید `device_token` به `players` اضافه شود |
| آواتار سفارشی (آپلود عکس) | فعلاً فقط `avatar_id` | آپلود فایل به object storage نیاز دارد، نه MongoDB |

## کارهای باقی‌مانده (مرحله بعد)

1. ~~احراز هویت~~ — اتصال/ورود با گوگل و توکن دستگاه انجام شد (بخش ۱.۱).
   ورود با ایمیل و رمز عمداً اضافه نشد؛ ایمیل از خودِ حساب گوگل می‌آید.
2. **امنیت حساب‌های مهمان**: حساب‌های وصل‌شده به گوگل کاملاً با توکن محافظت
   می‌شوند، ولی حساب مهمان هنوز فقط با `username` کار می‌کند (برای سازگاری با
   نسخه‌های قبلی). قدم بعد: الزام توکن برای همه‌ی حساب‌هایی که دستگاه دارند.
3. رتبه‌بندی صفحه‌بندی‌شده و نمایش رتبه‌ی خود بازیکن.
4. سیم‌کشی UI گودو به این اندپوینت‌ها (اسکریپت‌های profile / friends / messages).
5. رشد شهر: `level` و `experience` شهر هنوز هیچ‌جا بالا نمی‌روند و `max_members`
   ثابت ۵۰ است. وقتی مسابقه‌ی گروهی اضافه شد، `/match/result` باید به شهرِ
   شرکت‌کننده‌ها هم تجربه بدهد و ظرفیت با سطح شهر زیاد شود.
6. آیکن سفارشی شهر: `icon_path` در مدل هست ولی باکس ساخت شهر هنوز انتخابگر
   آیکن ندارد (مثل `avatar_picker` برای پروفایل).
